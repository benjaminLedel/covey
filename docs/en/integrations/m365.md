A runbook for the `m365` plugin. The agent gets a **Microsoft 365 user of its
own** and works in it the way a colleague does: it reads and answers its mail,
keeps its calendar, and finds, edits and files documents in OneDrive and
SharePoint. Everything goes through the Microsoft Graph API with an Entra ID
app registration.

> Short version: a licensed user for the agent, an app registration with
> application permissions, an Exchange scope that fences the app into that one
> mailbox, two secrets, one line in ACCESS.md, three egress hosts.

How it differs from its neighbours:

| | `m365` | `email` | `sharepoint` |
|---|---|---|---|
| Mail | Exchange Online through Graph | any IMAP/SMTP server, password login | — |
| Calendar | yes | — | — |
| Files | own OneDrive + every site the app may reach | — | one library behind a share link |

Exchange Online no longer accepts password logins over IMAP, so for a Microsoft
365 mailbox `m365` is the way, not `email`.

---

## 1. What the agent can do

- **Mail** — list a folder (unread only, or by search words), read a message as
  text with its attachment list, put an attachment into the sandbox, reply or
  reply to all (with sandbox files attached), send a new mail, leave a **draft**
  for a person to check and send, move a mail into a folder, mark it read.
- **Calendar** — read the calendar between two times (series expanded), create
  an event with attendees or as a Teams meeting, accept / decline / tentatively
  accept an invitation, cancel an event it organises, look up colleagues'
  free/busy times.
- **Files** — find SharePoint sites, list a site's libraries, list and search a
  library or its own OneDrive (`drive_id` `me`), read a text file, download a
  file into the sandbox, upload one from it, write a text file, create folders.
  There is **no delete action**, on purpose.
- **Office documents** — the plugin does not parse them. The agent downloads a
  `.docx`, `.xlsx` or `.pptx`, edits it in the sandbox with `python3`
  (`docx`, `openpyxl`, `pptx` are in the base workplace) and uploads it onto the
  same path.

Sending mail and inviting people reaches real people. The guard-rail subjects are
one per action (`m365:send_mail`, `m365:create_event`, …), so an organisation
that wants a human to look first puts `require_approval` on exactly those and
leaves reading free.

## 2. Setup

### 2.1 A user for the agent

Create a licensed user with a mailbox, e.g. `agent@contoso.com`. Its OneDrive
comes with the licence. A shared mailbox works for mail and calendar, but has no
OneDrive.

### 2.2 The app registration

Entra ID → **App registrations** → new app. Under **API permissions** →
Microsoft Graph → **Application permissions** add, then **grant admin consent**:

| Permission | For |
|---|---|
| `Mail.ReadWrite`, `Mail.Send` | the mailbox |
| `Calendars.ReadWrite` | the calendar |
| `Files.ReadWrite.All` | OneDrive and document libraries |
| `Sites.ReadWrite.All` — or `Sites.Selected`, see 2.4 | finding sites |

Create a **client secret** and put its expiry date in a calendar: after it, every
action fails with `invalid_client`.

### 2.3 Fence the app into the agent's mailbox

Application permissions hold **tenant-wide**. Without this step the app could
read every mailbox in the organisation. Exchange Online's RBAC for Applications
scopes it to the one user (Exchange Online PowerShell):

```powershell
New-ManagementScope -Name "covey-agent" `
  -RecipientRestrictionFilter "PrimarySmtpAddress -eq 'agent@contoso.com'"
New-ServicePrincipal -AppId <client-id> -ObjectId <enterprise-app-object-id> `
  -DisplayName "covey agent"
New-ManagementRoleAssignment -App <client-id> -Role "Application Mail.ReadWrite" `
  -CustomResourceScope "covey-agent"
New-ManagementRoleAssignment -App <client-id> -Role "Application Mail.Send" `
  -CustomResourceScope "covey-agent"
New-ManagementRoleAssignment -App <client-id> -Role "Application Calendars.ReadWrite" `
  -CustomResourceScope "covey-agent"
```

Then remove `Mail.*` and `Calendars.*` from the Graph permissions in Entra ID —
the scoped Exchange assignments carry them now. Check with
`Test-ServicePrincipalAuthorization -Identity <client-id> -Resource agent@contoso.com`
(and once with another mailbox, which must answer *not in scope*).

The plugin itself only ever addresses the mailbox in `m365_url`. That is a
convention of the code, not a boundary: the boundary is this step.

### 2.4 SharePoint with least privilege

`Sites.ReadWrite.All` lets the app into every site. With `Sites.Selected`
instead, it sees only the sites it has been granted, one by one:

```http
POST https://graph.microsoft.com/v1.0/sites/{site-id}/permissions
{ "roles": ["write"],
  "grantedToIdentities": [{ "application": { "id": "<client-id>", "displayName": "covey agent" } }] }
```

`list_sites` then shows exactly those.

### 2.5 Secrets, access, egress

Under **Secrets**, assigned to the agent:

```
m365_url   = agent@contoso.com
m365_token = <tenant-id>:<client-id>:<client-secret>
```

`m365_url` takes optional overrides after the address for national clouds:
`graph=https://graph.microsoft.us login=https://login.microsoftonline.us`.

In the agent's `ACCESS.md`:

```
- system: m365   scope: read,write
```

**Egress** — import the built-in template *Microsoft 365*, or add the hosts:

| Host | Why |
|---|---|
| `graph.microsoft.com` | the API |
| `login.microsoftonline.com` | the token |
| `*.sharepoint.com` | file downloads: `/content` redirects to the tenant's SharePoint host |

Without the third one, listing works and every download ends in `Forbidden`;
the egress log shows the refused CONNECT.

### 2.6 Testing

The connection test in *Settings → Target systems* reads the inbox and answers
`mailbox agent@contoso.com reachable: 3 unread of 41 in the inbox`. A **403**
there is nearly always 2.3: the app lacks the permission, or the Exchange scope
does not include the mailbox. The error says so, and retrying does not help.

## 3. Intake

There is no webhook: Graph change notifications need a publicly validated
subscription that has to be renewed every few days. The intake is a heartbeat
with a pre-check that costs one call:

```yaml
- alle: 10m nur-wenn: m365 titel: Look after the mailbox
  aufgabe: Read the unread mail (list_mail unread:true) and work on it by the playbook.
```

`nur-wenn: m365` asks for the unread mail in the inbox (`nur-wenn: m365:<folder>`
for another folder). It reports one item per message (`mail:<id>@<last modified>`),
so it fires when a mail arrives or changes and stays quiet while the inbox stands
still, and a [workflow](../../../spec/29-workflows.md) on `only_if: m365` runs one
case per mail. The agent's own `mark_read`, `move_mail` and `reply_mail` are
known to move the signature and do not wake it again.

Ids are Graph's **immutable ids**: a mail keeps its id when it is moved, so a note
or a workflow case that names it stays true.

## 4. Limits

| What | Limit |
|---|---|
| Attachments on an outgoing mail | 3 MB together (Graph refuses a request over 4 MB) — a larger file goes to OneDrive with `upload_file`, and the mail carries its link |
| An attachment fetched into the sandbox | `COVEY_M365_ATTACHMENT_MAX_MB`, default 25 |
| An upload | `COVEY_M365_UPLOAD_MAX_MB`, default and maximum 250 (simple upload) |
| `read_file` | text up to 1 MB; anything else through `download_file` |
| `list_mail` | 50 per call |
