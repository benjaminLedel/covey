# Org templates: a whole team at once, and a routing partition that can be checked

> How a template describes several agents and the relationships between them, how work is divided
> between them declaratively instead of in prose, and how the platform proves the division has neither
> a hole nor an overlap.

Related: [`20-hiring-and-setup.md`](20-hiring-and-setup.md) (the draft state, the People department,
`covey/create_agent` — this document leans on all three), [`21-agent-templates.md`](21-agent-templates.md)
(one agent's requirements, wizard and functional test — reused per member here),
[`02-agent-model.md`](02-agent-model.md) (org chart, config as code),
[`03-lifecycle-scheduling.md`](03-lifecycle-scheduling.md) (heartbeats, `nur-wenn`).

## 1. Why the unit is wrong today

A bundle is one agent. An organisation does not hire one agent; it staffs a **function** — a lead, two
or three developers, a reviewer, and the hand-offs between them. Every existing template dodges the
gap in the same visible way: `delivery-lead.bundle.json` tells its agent to delegate to
`{"agent":"<slug from the org chart>"}`, because at authoring time it cannot know who its colleagues
will be. That placeholder is the missing feature, written out in prose.

[`20`](20-hiring-and-setup.md) already produces several agents at once — the People department's
self-onboarding ends with *three* draft colleagues. That is the **generative** path: an LLM reads the
company description and proposes a team. It is the right answer when nobody knows yet what they need.
It is the wrong answer when they do: an organisation that runs the same delivery-team shape for the
fourth project does not want three fresh inventions, it wants the shape it already reviewed.

So the two paths are peers, not competitors, and they meet: the People department can *propose an org
template* ("I suggest the standard delivery team") instead of drafting from scratch, which turns its
recommendation into something a human can diff against a known-good structure.

### The evidence: what staffing a team by hand actually costs

This design is not speculative. Splitting one backend/frontend pair into three domain teams
(operations, onboarding, billing) plus a dedicated API-contract role took, by hand:

- **5 bundle files that were near-identical** — same `ACCESS.md`, same board stages, same two
  heartbeats, differing only in slug, display name, the domain labels each may claim, and which
  sibling it hands off to. They were not hand-written five times; they were generated by a throwaway
  Python function with the deltas as parameters. **Ad-hoc templating, invented in a scratch script,
  because the platform has none** — that is the clearest statement of the gap available.
- **~68 API calls**: one import per member, then per member three org-chart calls
  (supervisor, department, profile), three secret assignments and seven egress-template assignments.
  Every one of them identical in shape to its neighbours.
- **Two config rewrites of agents that were not part of the new work.** The pre-existing backend and
  frontend agents had to be *narrowed* — told which domains they no longer own — or they and the new
  teams would both claim the same issue. This is the deepest lesson in this document and § 5 is about
  it.
- **One near-miss.** A separate incident in the same fleet: the `order-system-api` component had 28
  issues assigned and **no agent that claimed it**, because the backend agent correctly recognised
  contract changes as outside its remit and declined them. Six backend stories sat blocked on API
  tickets nobody owned. Nothing in the platform noticed; a human found it by reading an escalation and
  reasoning backwards. § 6 makes that a check.

## 2. Scope

**In scope.** A second bundle kind describing members and their relationships; composition from
existing single-agent templates; intra-bundle references; fan-out of a role; a declarative routing
partition with generated filters; org-level verification (coverage, references, hygiene); the apply
order.

**Out of scope.** Shared boards (each agent owns its own — [`internal/backlog`](../internal/backlog),
and delegation plus task parenthood already covers cross-agent work). Cross-organisation templates.
Any form of automatic hiring — see § 8.

## 3. The org bundle

A new `kind`, not a v3 of `covey.agent-config`. The unit is genuinely different — a set plus
relations — and overloading the existing kind would make every consumer branch on "is this one agent
or many" for the rest of its life.

```json
{
  "kind": "covey.org-template",
  "version": 1,
  "name": "Software delivery team",
  "description": "A lead, per-domain developer pairs, a reviewer, and the hand-offs between them.",

  "inputs": [
    { "key": "prefix",   "label": "Slug prefix", "kind": "text",  "required": true, "default": "it" },
    { "key": "owner",    "label": "Accountable human", "kind": "human", "required": true },
    { "key": "domains",  "label": "Domains to staff separately", "kind": "multi", "required": true }
  ],

  "departments": [
    { "key": "eng", "name": "Engineering", "color": "#4c7a8c", "lead": "@member:arch" }
  ],

  "members": [
    { "key": "arch", "slug": "{{input:prefix}}-arch", "from": "delivery-lead",
      "department": "@dept:eng", "supervisor": "@human:{{input:owner}}",
      "job_title": "Architect", "effort": "high" },

    { "key": "api", "slug": "{{input:prefix}}-api", "from": "coding-agent",
      "department": "@dept:eng", "supervisor": "@member:arch",
      "overrides": { "files": { "SOUL.md": "…contract-only remit…" } } },

    { "key": "backend", "slug": "{{input:prefix}}-backend-{{fanout:key}}", "from": "coding-agent",
      "department": "@dept:eng", "supervisor": "@member:arch",
      "fanout": { "over": "@input:domains" } }
  ],

  "routing": { "…": "see § 4" },
  "adjusts": [ "…": "see § 5" ],
  "verify":  { "…": "see § 6" }
}
```

### 3.1 Composition, not duplication

`from` names an existing single-agent template; `overrides` is a deep merge on top of it. This is the
direct answer to the five near-identical files: a member says what makes it *different*, and the
platform assembles the rest. A member without `from` may inline a full `files` map — a team of
genuinely unrelated roles should not be forced through a fake common ancestor.

The merge is a **file-level replace inside a key-level merge**, exactly like upstream's
`set_agent_config` (`spec/20`, § *covey self-service*), and for the same reason it was fixed there: a
whole-set replace silently deletes what an earlier layer wrote, and the result looks complete. An
override of `SOUL.md` replaces `SOUL.md` and leaves `PLAYBOOKS.md` alone.

### 3.2 References resolve at apply time

| Reference | Resolves to |
|---|---|
| `@member:<key>` | another member of this bundle — the whole point; keys are stable, slugs are input-templated |
| `@dept:<key>` | a department declared in this bundle |
| `@human:<email>` | an existing human, for the accountable owner |
| `@existing:<slug>` | an **existing** agent — a new team hanging under a manager who is already there, the common real case |
| `@input:<key>` | an input value, for fan-out sets |

A reference that does not resolve is a blocker, not a warning: a supervisor that silently ends up
`null` produces an agent nobody is accountable for, and § 6 would rather refuse than report it.

### 3.3 Fan-out requires a partition

`fanout.over` stamps one member definition N times — one per value of a `multi` input — suffixing the
slug. This is where a well-meant feature becomes the bug it was meant to prevent: **three identical
developer agents polling the same work list all claim the same ticket.** Therefore fan-out is only
accepted together with a routing rule that keys on the fan-out dimension (§ 4). No partition, no
fan-out — the platform refuses the bundle rather than producing a team that duplicates itself.

## 4. Routing: the partition becomes data

Today an agent's share of the work is a sentence in its `HEARTBEAT.md` — hand-written, per agent,
unchecked. What that produced in practice is in § 1: prose that had to be edited in three places to
stay consistent, and a hole nobody noticed for days.

```json
"routing": {
  "source": "gitlab:issues:assigned",
  "dimension": "label",
  "rules": [
    { "member": "billing",    "match": ["domain::invoice"],                 "priority": 20 },
    { "member": "onboarding", "match": ["domain::master-data",
                                        "domain::saas",
                                        "domain::user-management"],         "priority": 10 },
    { "member": "api",        "match": ["component::api"],                  "priority": 10 },
    { "member": "backend",    "match": ["*"],                               "priority": 0 }
  ]
}
```

Three properties earn their keep:

**Precedence is explicit.** An issue labelled both `domain::invoice` and `domain::master-data` goes to
billing because 20 beats 10. By hand this had to be written into every affected agent's prose as
"*`invoice` takes precedence*", in every one of them, consistently. One number replaces that.

**The catch-all is visible.** A rule matching `*` is what stands between a backlog and starvation. Its
*absence* is the `component::api` incident, and § 6 refuses a bundle that has no catch-all unless the
author waives it deliberately (`"allow_unrouted": true`) — because sometimes a partial partition is
right, and then it should be a decision rather than an oversight.

**The filter text is generated, not written.** Each member's `HEARTBEAT.md` sighting run gets its
filter rendered from this table at apply time. The prose and the declaration therefore cannot drift,
because there is only one of them. That is the same argument [`21`](21-agent-templates.md) § 4 makes
about requirements: a second source of truth for something the platform already knows will rot, and a
rotted one reads as authoritative.

### 4.1 The better shape, and the honest gap

Rendering the filter into each agent's config still leaves the routing table *copied* into N configs.
Adding a fourth team then means re-rendering the other three — cheap and mechanical, but still a write
to agents that were not the subject of the change (§ 5).

The cleaner target is that the routing table lives **on the department as data**, and the heartbeat's
own work-check consults it at wake time — so a member's config never contains a filter at all, and
adding a team is one edit to one table. That needs a real change to how `nur-wenn` gates work
([`03-lifecycle-scheduling.md`](03-lifecycle-scheduling.md)): the check would take the calling agent's
routing share as an argument instead of asking a per-agent question. It is the right end state and it
is not a spec detail — recorded as D8.

Until then: generate at apply time, re-render on change, and let § 6 catch a stale render.

## 5. Adopting agents that already exist

The lesson from § 1 that has no obvious home: **staffing a new team usually requires changing agents
that are not in the template.** The three-domain split could not be applied without narrowing the two
pre-existing agents, and a template that can only add is a template that quietly ships the overlap it
was supposed to prevent.

```json
"adjusts": [
  { "agent": "@existing:it-backend",  "reason": "loses the domains the new teams take over" },
  { "agent": "@existing:it-frontend", "reason": "same" }
]
```

Two constraints keep this from becoming a licence to rewrite live agents:

1. **Only the generated part.** An `adjusts` entry brings the named agent into the routing table and
   re-renders *its filter*, nothing else. Its `SOUL.md`, its playbooks, its access are untouched.
   Arbitrary edits to a working colleague's config are exactly what config-as-code exists to make
   deliberate ([`02`](02-agent-model.md)) — and this is not that.
2. **It shows as a diff and needs the same confirmation as a hire.** The plan renders the before/after
   of each adjusted agent's filter. Nothing is written to a *hired, running* agent without a person
   seeing what changes.

`reason` is mandatory and ends up in the audit entry. An adjustment without a stated reason is the
kind of change that is impossible to review six weeks later.

## 6. Verification: T5, the org tier

[`21`](21-agent-templates.md) § 8 defines four per-agent tiers (config, platform, credentials, smoke).
They all still apply, per member. What no per-agent check can see is whether the *set* is coherent, so
one tier is added — and unlike T4 it is free, because it is pure set arithmetic over declarations.

**T5.1 — Partition.** Build the label/dimension matrix from the routing table plus, where a credential
is already available, a real sample of open work items from the source system. Every item must map to
**exactly one** member.

- zero → **starvation**, blocker. This is the `component::api` incident, found statically in
  milliseconds instead of by a human reading an escalation three days later.
- more than one → **duplicate work**, blocker. This is the bug the hand-rolled split would have
  shipped without the two manual narrowings.
- a rule that can never win (fully shadowed by a higher priority) → warning: dead configuration is
  usually a typo in a label.

**T5.2 — References and graph.** Every `@member:`/`@dept:`/`@human:`/`@existing:` resolves. The
supervisor graph over *all* affected agents is acyclic — note that the existing per-edge cycle check
(`handleSetSupervisor`) cannot catch a cycle a bundle introduces by applying several edges at once.
Every delegation target named in any member's config (`covey/create_task` with an `agent` field) is
either a member of this bundle or an existing agent; a template that tells an agent to hand work to a
colleague who does not exist produces a run that fails at the last step.

**T5.3 — Hygiene.** Members with no supervisor, departments with no lead, a member nobody can reach
and that reaches nobody. Each a warning, not a blocker — a deliberately isolated agent is legitimate,
an accidentally isolated one is a Friday-afternoon mistake, and only a human can tell them apart.

This is also the first org-wide check the platform has at all: today the only thing of this kind is a
*"without supervisor"* hint in the org-chart page. `POST /api/v1/org/verify` therefore runs T5 against
the **live** organisation, not only against a pending bundle, which turns "did our staffing drift?"
into a query.

## 7. Apply

The two-pass shape is not invented here — [`demo/seed`](../demo/seed) already staffs ten agents across
three departments this way, because agent A's supervisor may be agent B, which does not exist yet, and
its `supervisor` field is deliberately either a human's e-mail or a colleague's slug, resolved against
both maps in the second pass. Adopting it verbatim:

1. **Pass 1 — create.** Departments, then every member as a **draft**
   ([`20`](20-hiring-and-setup.md): `hired_at IS NULL`). Config, board stages, profile.
2. **Pass 2 — wire.** Supervisors, department membership, department leads — now that every key
   resolves to an ID.
3. **Requirements.** The per-member plans from [`21`](21-agent-templates.md), **unioned**: a team of
   six agents that all need `gitlab_token` asks the human once, not six times. That union is most of
   the ~68 calls from § 1 collapsing into one screen.
4. **Render** the routing filters into the members and, if `adjusts` is set, into the adjusted agents
   (after the diff was confirmed).
5. **Verify.** T1–T3 per member, then T5 for the set.
6. **Hand over.** One review surface listing every draft, its role, what it asks for, and its
   verification result.

The draft state is what makes this safe, and it is worth being explicit about why: **a half-applied org
costs nothing.** Six drafts that turn out wrong are edited or discarded with no recording, no cost and
no trace — [`20`](20-hiring-and-setup.md) § *The draft state*. An org template without a draft state
would be a feature that creates six live, half-configured agents on a bad afternoon. This design should
therefore not be built before it.

## 8. Hiring stays a human act — at team scale too

[`20`](20-hiring-and-setup.md) closes with the rule that carries this document as well: there is no
`hire` action, *"not a forbidden one — a missing one, so there is nothing to forget to check."*
Nothing here changes that, and the temptation is real: an org template already knows the whole team, so
"apply and hire" is one obvious button away.

It does not get built. What an org template produces is N drafts and **one review surface**; a person
still hires — either each member, or all of them in one deliberate act on that surface, which is a
decision about a team rather than a shortcut around the decision. An agent may hold
`covey scope: agents:write` and instantiate an org template, exactly as the People department may draft
individuals — and its output is drafts, the same as everything else it produces.

Also unchanged: **an org template grants no access.** Members ask for target systems; the requests go
down the existing approval path. A template that could staff six agents *and* hand them six tokens
would be a single reviewable object that quietly answers "who may reach which system" — which is the
one question this platform insists a human answers.

## 9. Build order

Every slice useful alone, and the cheap correctness win first:

| M | Content | Why here |
|---|---|---|
| **M1** | `POST /api/v1/org/verify` — T5.2 + T5.3 against the **live** org, no templates involved | The platform has no org-wide check at all today; this pays off on the existing fleet before a single template exists |
| **M2** | The org bundle, `from`/`overrides`/references, two-pass apply into drafts, unioned requirements | The core; leans entirely on machinery that already exists |
| **M3** | Routing table + generated filters + T5.1 partition check | The part that prevents the two real bugs from § 1 |
| **M4** | `adjusts` with its diff, and `fanout` (which T5.1 now makes safe) | Both need M3 to be anything but dangerous |
| **M5** | The People department proposing an org template instead of three inventions | The generative and declarative paths meeting |

## 10. Open decisions

- **D6 — One review surface or N.** A team of six produces six drafts. Recommended: one surface for
  the set, with per-member expand — the alternative is six hire dialogs in a row, which is how people
  learn to click through them. Open: whether rejecting the set deletes all drafts or leaves the
  accepted ones.
- **D7 — Routing dimensions beyond labels.** Labels cover GitLab and most ticket systems. A mail-driven
  team would partition by recipient or folder, an on-call rota by time. Recommended: ship
  `dimension: label` only, and let the second real case shape the abstraction rather than guessing it
  now.
- **D8 — Where the routing table lives.** Rendered into each member's config (this document, § 4) or
  read from the department at wake time (§ 4.1, the better end state). The second removes `adjusts`
  almost entirely and needs a change to the `nur-wenn` work-check signature. Recommended: build M3 as
  rendered, revisit before M4 — if it is done, `adjusts` shrinks to a one-time migration for
  hand-written agents.
- **D9 — Templates that describe humans.** Departments have human leads and members have accountable
  owners, but a template cannot create a human and should not. Open only in the sense that a template
  currently *requires* the human to exist first, which is correct and slightly annoying.

## 11. Definition of done

1. `POST /org/verify` on the existing 27-agent fleet reports the real findings: agents with no
   supervisor, and any delegation target named in a config that does not exist.
2. A `component::`-shaped hole (a label with issues assigned and no member claiming it) is a T5.1
   blocker naming the label — the `order-system-api` incident, caught statically.
3. Two members whose rules both match the same label is a T5.1 blocker naming both — the overlap the
   hand-rolled split avoided only by manual narrowing.
4. `fanout` without a rule keyed on the fan-out dimension is refused at parse time.
5. Applying a template produces only drafts; a failure in pass 1 or 2 leaves no agent behind, and no
   hired agent is ever modified without a confirmed diff.
6. Six members needing the same secret ask for it once.
7. Instantiating the delivery-team template twice with different `prefix` inputs produces two
   independent teams whose members delegate within their own team, never across.
8. No path in this document sets `hired_at`.
